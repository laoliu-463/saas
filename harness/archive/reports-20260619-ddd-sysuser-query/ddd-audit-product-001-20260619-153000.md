# DDD-AUDIT-PRODUCT-001 审计报告

## 1. 现象与证据

### 1.1 商品快照与运营状态的物理分离
*   **现象**：系统将商品数据分为“快照数据（外部数据）”与“运营/展示状态（内部数据）”两部分进行维护。
*   **证据**：
    *   `ProductSnapshot` 对应 `product_snapshot` 表，存储由抖店 API 同步的最新商品信息。其主键 UUID 在 `ProductService.java` 中通过哈希生成（`buildSnapshotId(activityId, productId)`）。
    *   `ProductOperationState` 对应 `product_operation_state` 表，存储商品的分配负责人（`assigneeId`）、本地发布状态（`manualDisabled`）、展示状态（`displayStatus`）和审核状态。
    *   两表无外键关联，逻辑上依靠 `(activityId, productId)` 绑定，查询层使用 `toLegacyProduct()` 动态拼接成 DTO 输出到前端。

### 1.2 同步与去重策略的强耦合
*   **现象**：当商品快照同步（无论是增量还是 Backfill）发生时，跨活动展示去重规则引擎会被同步触发。
*   **证据**：
    *   在 `ProductService.java#upsertSnapshotsWithStats` 中，同步流程会对每个 Item 调用 `applyUpstreamProductLibraryDecision` 更新状态。
    *   同步完成后紧接着调用 `productDisplayRuleService.repairLibraryStateForActivity()` 和 `applyForActivityId()` 触发展示去重重算，产生跨活动的数据查询和行锁更新。

### 1.3 快速寄样（Quick Sample）的跨域依赖
*   **现象**：商品域直接承载了“快速寄样”这一典型的寄样域业务编排逻辑。
*   **证据**：
    *   `ProductController.java` 的 `quickSample` 接口映射为 `/products/{relationId}/quick-sample`。
    *   该接口直接注入并依赖了 `ProductQuickSampleApplicationService.java`，而在服务实现中，商品域不仅要读取 `product_snapshot`，还要处理寄样表单创建、私海达人逻辑，横跨两个核心限界上下文。

---

## 2. 推论与阶段性结论

### 2.1 性能与锁竞争风险
*   **推论**：当前商品展示去重引擎是跨活动决策的（相同的 `productId` 在不同活动下竞争展示）。在多线程高并发同步快照或跑大量 Backfill 同步时，由于去重规则是在同一个同步事务中执行，会导致频繁的跨活动记录加锁，极易触发死锁（Deadlock）和行锁等待超时。

### 2.2 限界上下文边界模糊
*   **推论**：商品域目前不是纯净的“商品及转链”元数据上下文。它强依赖了寄样业务，使 `domain/product` 包与 `domain/sample` 存在双向或越界依赖，增加了未来的重构和维护成本。

### 2.3 审计结论
*   商品域与寄样域、配置域的边界急需厘清，必须建立商品域专属的只读 Facade（`ProductReadFacade`），并将寄样相关逻辑物理迁移至寄样限界上下文。

---

## 3. 下一步任务

1.  **【测试先行】(TDD)**：编写 `ProductDisplayRuleServiceTest` 架构防护测试，锁定当前去重竞争逻辑，确保重构时不破坏既有业务优先级规则（置顶 > 投流 > 高佣金 > 晚上架）。
2.  **【Facade 建立】**：设计 `ProductReadFacade` 接口，暴露商品元数据、转链映射等只读方法。
3.  **【逻辑搬迁】**：将 `ProductQuickSampleApplicationService` 迁移至 `domain/sample/application` 下，改由 `SampleApplicationService` 编排，商品控制器调用寄样域入口，使商品域不再反向依赖寄样逻辑。
4.  **【事务解耦】**：将商品快照同步与去重计算解耦，在同步完毕后通过发布 `ProductSnapshotSyncedEvent` 异步进行展示去重或定时对账。

---

## 4. 风险评估

*   **同步与去重解耦期间的状态不一致**：在快照写入与去重计算的时间差内，可能会有极短暂的商品展示状态滞后。可以通过优化对账和优先处理高优商品来降低影响。
*   **Facade 迁移对老接口的冲击**：在重构 `ProductController` 阶段，需确保前端过渡 API 不受影响。
